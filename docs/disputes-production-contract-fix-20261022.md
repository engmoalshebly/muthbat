## السبب المؤكد

عرض الجهاز رسالتين مستقلتين:

- `PGRST202` عند استدعاء `add_dispute_message` بأربعة معاملات، تشمل `p_sender_workspace`. فحص سجل المشروع `sgnbtrcbllnffcyzsjei` أكد أن آخر ترحيل منشور كان `20261021214149`؛ ترحيل الدالة المطلوبة `20261022101957` لم يكن منشورًا.
- `42501 permission denied for table businesses` عند تحديث ملف المؤسسة. التطبيق كان يرسل `country_code` و`updated_at` بينما دور `authenticated` يملك صلاحيات تحديث على أعمدة محددة فقط، لا تشمل هذين العمودين.

رفع الكود إلى GitHub أو إعادة بناء التطبيق لا ينشر ترحيلات Supabase تلقائيًا.

## الإصلاح المنشور

نُشرت الترحيلات التالية بنجاح باستخدام CLI بعد استعادة صلاحية الوصول للمشروع:

- `20261022101957_dispute_message_sender_workspace.sql`
- `20261022141321_repair_profile_and_dispute_contract.sql`

يتيح الإصلاح دالة الرد الجديدة، ويحافظ على توافق الاستدعاء القديم للزبون والتاجر. التحقق من صاحب الحساب ودوره والاعتراض يتم داخل الدالة المحمية. إعادة الطلب بالمعرّف نفسه لا تكرر الرسالة، وتُرفض إعادة الطلب مع تغيير محتواه أو صفة مرسله. تُرفض الرسائل الفارغة أو الطويلة وصفة الإرسال الفارغة، ولا يسمح للمستخدم المجهول بالتنفيذ.

صلاحية تحديث المؤسسة أضيفت لعمود `country_code` فقط. بقيت الملكية و`updated_at` غير قابلتين لتعديل العميل، وبقيت RLS مسؤولة عن ملكية السجل.

## إصلاح التطبيق

- تقتصر حمولة تحديث المؤسسة، بما فيها الطلبات القديمة، على الحقول القابلة للتحرير. لا يُعلن نجاح الحفظ إلا عندما يرجع الخادم معرّف السجل المطلوب.
- يُمنع تعديل ملف مؤسسة أخرى محليًا. لا تستبدل تحديثات الخادم بيانات المؤسسة المعدلة محليًا أثناء انتظار طلب حفظها، حتى عند تعثره.
- تتحقق المزامنة من `client_sync_contract()` قبل استعادة الطلبات المتوقفة بسبب الخطأين المحددين. الاستعادة مرة واحدة لكل طلب؛ لا تتغير الحمولة ولا معرّف الطلب. لا تعاد أخطاء صلاحيات الأعمال الأخرى تلقائيًا.
- يشترط إرسال رد الاعتراض رجوع معرّف رسالة صحيح من الخادم قبل إزالته من الطابور.
- أصبح عنوان العملية المتوقفة يوضح أنها رد اعتراض أو تحديث مؤسسة.
- أصبحت إضافة عمود `sender_workspace` المحلي قابلة لإعادة التنفيذ دون خطأ عمود مكرر عند ترقية قواعد أقدم.
- إصدار التطبيق `0.2.1+3`.

- `033_customer_dispute_followup.sql` ناجح على الخادم بعد النشر: ردود الطرفين، إعادة الطلب، حل الاعتراض، عدم تكرار التصحيح المالي ومنع عميل آخر.
- `035_profile_dispute_contract.sql` ناجح على الخادم: تحديث ملف المالك، حماية أعمدة الملكية والتوقيت، استدعاء الرد القديم والجديد، رفض انتحال الصفة وتغيير الطلب، وعدد إشعارات الردود ووجهة مساحة العمل الصحيحة.

- مجموعة Flutter الكاملة: **180 اختبارًا ناجحًا**. يشمل ذلك استعادة الطلبات بمعرّفاتها الأصلية بعد تأكيد نشر العقد، وعدم الاستعادة قبل النشر، وحماية تعديل المؤسسة المحلي، وعدم اعتبار تحديث غير مؤكد نجاحًا.

## حدود التحقق والإطلاق

هذا تحقق لدورة الاعتراضات والعقد المعالج، وليس شهادة شاملة لكل خصائص المنتج. لم تُرسل رسالة فعلية باسم المستخدم لإثبات وصولها على جهازَي التاجر والزبون. اختبارات SQL تثبت إنشاء إشعارات قاعدة البيانات؛ وصول push عبر FCM يحتاج تجربة جهازين.

فحص Supabase Security Advisors كشف أيضًا توصيات سابقة مستقلة عن الإصلاح، منها صلاحية تنفيذ مجهولة للدالتين `rls_auto_enable` و`update_business_currencies`، وتعطيل حماية كلمات المرور المسربة. لم يوسع هذا الإصلاح تلك الصلاحيات؛ يلزم تقييمها في مراجعة الأمان العامة قبل إطلاق واسع.

لا تمسح بيانات التطبيق ولا تعِد تثبيته بعد حذفه؛ الرسائل غير المرسلة محفوظة محليًا. حافظ على إعداد البيئة المستخدم في النسخة الحالية، لأن دفاتر `staging` و`prod` مفصولة محليًا حتى إن استهدفتا المشروع السحابي نفسه. تشغيل `tool/run-cloud.ps1` يستخدم حاليًا `config/supabase.cloud.json` (`APP_ENV=staging`).
