# مشروع Supabase السحابي

المشروع المطلوب: `sgnbtrcbllnffcyzsjei`.

الحزمة مثبتة، و`main.dart` يهيئ Supabase بالفعل، بما يشمل محرك المزامنة والخلفية. بيانات المشروع العامة في `config/supabase.cloud.json`. إعداد dev الافتراضي يتصل بهذا المشروع أيضًا، ويمكن تجاوزه بمتغيرات البناء الحالية. لا تستخدم مفتاح service_role أو مفتاحًا سريًا داخل التطبيق.

## تشغيل مُثبَت

من جذر المستودع:

```powershell
./mobile/tool/run-cloud.ps1
```

أو من `mobile`:

```powershell
./tool/run-cloud.ps1
```

لجهاز محدد: `./mobile/tool/run-cloud.ps1 -DeviceId DEVICE_ID`.

يستخدم السكربت وضع `Release` افتراضيًا ليتوافق مع نسخة APK الموقعة المثبتة من هذا المشروع، ويحافظ على بيانات التطبيق. يمكن اختيار `-Mode Debug` عند الحاجة إلى hot reload، لكن مفتاح debug مختلف ولا يمكنه تحديث نسخة release بالمعرف نفسه. وجود التطبيق في ملف مستخدم آخر على الهاتف قد يمنع تثبيت debug أيضًا. لا تحذف التطبيق لحل التعارض إذا كانت لديه عمليات غير متزامنة؛ استخدم نسخة بالمفتاح المطابق. نسخة Google Play قد تستخدم مفتاح Play App Signing المختلف عن مفتاح الرفع المحلي.

لا يحل مثال Todos محل شاشات مُثبَت. التطبيق يستخدم مخططه الحالي وترحيلاته، ويحتاج جداول المستخدمين والمحلات والعملاء والدفتر المالي والوظائف والسياسات.

## حالة الفحص الأولي

### الحالة الحالية بعد التهيئة — 18 أكتوبر 2026

- رُبط Supabase CLI بالمشروع `sgnbtrcbllnffcyzsjei` وطُبقت الترحيلات الأصلية الـ39، ثم ترحيل أمني جديد؛ الإجمالي 40.
- أُنشئ 39 جدولًا عامًا و9 جداول خاصة. كل الجداول العامة تفعّل RLS.
- أُنشئت حاويات `avatars` و`ledger-documents` و`statements` الخاصة و`business-assets` العامة للشعارات.
- أُصلح عرض `ledger_timeline` بتمكين `security_invoker`. أعاد فحص Supabase الأمني بمستوى `error` صفر نتائج.
- نُشرت 12 Edge Function، باستثناء مسار التسجيل التجريبي المباشر.
- أُنشئت أسرار مستقلة لتشفير الهاتف وبصمته والعامل الخلفي. النسخة المحلية في `debt-ledger-supabase/.verification/cloud-setup/.env` مستثناة من Git؛ احتفظ بها في مدير أسرار قبل تنظيف ملفات التحقق، ولا تغير مفاتيح الهاتف بعد تخزين بيانات مشفرة دون خطة ترحيل.
- ضُبطت بيئة الخدمات على `staging` وعُطل تجاوز التسجيل المباشر والتسجيل العام. مدة JWT هي 900 ثانية. لا توجد قيم OTP اختبارية مضافة إلى المشروع السحابي. بقي التخزين المتجهي معطلًا.
- نجح اختبار سحابي داخل معاملة تم التراجع عنها: دين 100 ودفعة 25، وإعادة الدفعة دون تكرار، ومطابقة الرصيد 75 والمحاسبة، ومنع حساب آخر من قراءة الحركات عبر `ledger_timeline`.
- الفحوص العامة أعادت 401 للدفتر وخدمة دليل العملاء دون جلسة مستخدم، و422 لطلب تحقق OTP فارغ.

**وضع التسجيل الحالي:** رقم الهاتف وكلمة المرور دون OTP، بطلب المستخدم. فُعّل Phone Auth، ونُشرت وظيفة `phone-password-signup` ليصبح العدد 13، وضبط سر الخادم `ALLOW_PHONE_PASSWORD_SIGNUP=true`. التسجيل العام المباشر إلى Supabase مغلق؛ وظيفة التسجيل تتحقق من المدخلات وتحد الطلبات ثم تنشئ حسابًا بعلامة خادمية تبين أن ملكية الهاتف لم تتحقق. لم تضبط بيانات OpenWA ولا يرسل التطبيق رموز تحقق في هذا الوضع. مزود Push مضبوط على `in_app`.

نجح اختبار سحابي لإنشاء حساب بكلمة مرور والدخول به ورفض كلمة خاطئة ووجود ملف العميل ومنع المطالبة بسجلات هاتف سابقة غير متحققة. حُذف الحساب المؤقت وسجل العميل بعد الاختبار. نجحت اختبارات Flutter الـ59 وفحص ملفات المصادقة.

إعداد تطبيق staging يفعّل إرسال رمز الهاتف عبر `PHONE_VERIFICATION_ENABLED=true`، بينما يظل تفعيل مزود OTP خادميًا خاصًا بكل مشروع. لا تربط الحسابات القديمة بسجلات العملاء تلقائيًا، واسترداد كلمة المرور لا يثبت ملكية الحساب إلا بعد استهلاك تحدي OTP صالح.

تجربة OTP على staging تستخدم `send-whatsapp-otp` لإنشاء التحدي خادميًا ثم ترسل الرمز عبر OpenWA `messages/send-text`. يجب إعداد `WHATSAPP_OTP_ENABLED=true` و`OPENWA_BASE_URL` و`OPENWA_SESSION_ID` و`OPENWA_API_KEY` كأسرار staging، مع إعادة إصدار نسخة التطبيق بعد ضبط `PHONE_VERIFICATION_ENABLED=true`. الإنتاج يبقى معطلًا حتى اختبار التسليم ومراجعة الترحيل. الحسابات المنشأة دون تحقق تحتاج مسار إثبات ملكية مستقل قبل رفع علامة `phone_verification_bypassed`؛ تغيير مفتاح البناء لا يثبت ملكية أرقام الحسابات القديمة.

تُدار إعدادات Phone Auth الحالية عبر Management API بتغيير `external_phone_enabled=true`, `disable_signup=true`, `sms_autoconfirm=true`. انتبه إلى أن `supabase config push` مع جميع مزودي SMS معطلين قد يعطل Phone Auth مرة أخرى؛ راجع `/auth/v1/settings` بعد أي نشر إعدادات.

يمكن إعادة التحقق بأوامر من جذر المستودع:

```powershell
supabase db query --linked --workdir D:/Dafter/debt-ledger-supabase --file D:/Dafter/debt-ledger-supabase/tools/verify-cloud-schema.sql
supabase db advisors --linked --workdir D:/Dafter/debt-ledger-supabase --type security --level error
```

### سجل الحالة قبل منح الوصول

في 18 أكتوبر 2026 استجاب `/auth/v1/health` بالرمز 200 باستخدام المفتاح العام، وأعاد فحص `businesses` مع `limit=0` الرمز `PGRST205`: الجدول غير متاح في مخطط REST. هذا الفحص لم يقرأ صفوف مستخدمين.

لم يظهر المشروع ضمن قائمة مشاريع حساب Supabase CLI الحالي. محاولة `supabase link` في مجلد عمل معزول أعادت رفض وصول صريحًا: `Your account does not have the necessary privileges`. لم تتغير وصلة المشروع القديمة ولم تطبق ترحيلات على مشروع آخر. المفتاح publishable يكفي للعميل ولا يمنح صلاحية إنشاء الجداول أو تطبيق الترحيلات.

تم تحديث `supabase_flutter` إلى `^2.18.3`. نجح فحص ملفات التهيئة و`main.dart` والمزامنة الخلفية دون مشكلات، ونجحت اختبارات Flutter الـ59 بعد التحديث. ملف JSON صالح نحويًا، وفُحصت صياغة سكربت PowerShell دون تشغيل التطبيق على جهاز.

## تهيئة الخادم

يلزم دخول Supabase CLI بحساب مخوّل للمشروع. احتفظ بكلمات المرور والأسرار داخل أدوات الاعتماد المحلية أو مدير أسرار.

```powershell
supabase login
supabase projects list
```

قبل تهيئة مشروع جديد، افحص حالة القاعدة وتاريخ الترحيلات. يوجد الآن 40 ترحيلًا في `debt-ledger-supabase/supabase/migrations`، ويجب تطبيقها بترتيبها الأصلي. لا تستورد `full_schema.sql` إضافةً إلى الترحيلات؛ قد يمثل إصدارًا أقدم ويكرر التعريفات.

يحتاج عمل التسجيل والاسترداد والعملاء والمرفقات والكشوف نشر Edge Functions وإعداد أسرار الهاتف وOpenWA. لا تكفي تهيئة Flutter وحدها لتفعيل هذه المسارات. يلزم استخدام إعداد Auth المخصص للبيئة، وتجنب رفع قيم OTP الاختبارية من الإعداد المحلي إلى مشروع عام.
